# Внутрипроцессная шина

Внутрипроцессная publish/subscribe шина событий для Linux. Потокобезопасная
публикация, асинхронная доставка через фиксированный пул потоков,
мониторинг состояния. Внешние брокеры не
используются. Готовые решения не применяются — только стандартная
библиотека C++20.

---

## 5. API шины

```cpp

class IEventBus : public utils::NonCopyable
{
    public:
        virtual utils::SubscriptionId Subscribe(const std::string& topic, utils::Handler handler) = 0;
        virtual void Unsubscribe(utils::SubscriptionId subId) = 0;
        virtual void Publish(const std::string& topic, const std::string& payload) = 0;
        virtual void Shutdown() = 0;
        virtual utils::MonitoringSnapshot Monitor() = 0;
};
```

`Handler` — любая вызываемая сущность с сигнатурой
`void(const std::string&, const std::string&)`.

## 6. Модель данных

### 6.1 Топики

Шина не ограничивает набор топиков. Поддерживаются как минимум
требуемые ТЗ:

| Топик | Назначение | Пример payload |
|---|---|---|
| `robot.state` | Состояние робота | `state=Idle;mode=Auto` |
| `robot.error` | Диагностические ошибки | `code=42;msg=joint_limit` |
| `io.digital`  | Дискретные сигналы | `pin=3;value=1` |

### 6.2 Формат payload

**Выбран строковый формат `key=value;...`** — единый для всех топиков,
пригоден для журналирования.

Обоснование:

- не требует сериализации и внешних зависимостей;
- читается в логах без декодера;
- допускает любые пары `ключ=значение`, включая будущие поля;
- одинаково удобен для всех трёх топиков.

## 7. Модель доставки — зафиксирована

**Асинхронная, через внутреннюю очередь и фиксированный пул потоков.**

ТЗ требует явно зафиксировать выбранную модель — фиксирую:

1. `Publish` не вызывает `handler` в своём контексте.
2. `Publish` под общим мьютексом `m_busMtx` снимает снимок
   подписчиков топика, затем под локом каждого `Subscriber`
   (`m_subMtx`) кладёт сообщение в его FIFO-очередь.
3. Для подписчика, у которого ещё нет активной задачи `Drain` в пуле,
   ставится ровно одна такая задача (флаг `m_isBusy`).
4. Рабочий поток пула (`tpool::ThreadPool`) выполняет `Drain`:
   последовательно вынимает сообщения из очереди подписчика и вызывает
   `handler(topic, payload)`. Бюджет — 64 сообщения
   (`m_drainBudget`) на одну задачу, затем `Drain` пере-постит себя,
   если очередь не опустела (медленный подписчик не монополизирует
   поток пула).
5. `Publish` возвращается сразу после постановки в очереди — он
   не блокируется на пользовательском коде.

## 8. Правила поведения — как выполнены

### 8.1 Произвольное число подписчиков на топик

`m_subByTopic[topic]` — `std::vector<std::shared_ptr<Subscriber>>`.
Ограничения на количество нет; на один топик можно подписаться
неограниченное число раз.

### 8.2 Сообщение доставляется всем активным на момент публикации

`Publish` в начале под `m_busMtx` копирует вектор подписчиков топика.
Дальше работа идёт со снимком: подписки/отписки, случившиеся после
снимка, на эту публикацию не влияют.

### 8.3 FIFO для пары «один publisher — один subscriber»

Гарантия опирается на два инварианта:

- очередь подписчика — FIFO (`std::queue`), порядок `push` = порядок
  вызовов `Publish` из одного потока-издателя;
- у подписчика одновременно не более одной активной `Drain`
  (`m_isBusy`), поэтому порядок `pop` = порядок `push`.

Для двух разных издателей FIFO между ними не гарантируется

### 8.4 После `Unsubscribe` подписчик не получает сообщения

`Unsubscribe(subId)` выполняет:

1. Удаляет `Subscriber` из `m_subById` и `m_subByTopic` под
   `m_busMtx`. Новые `Publish` его уже не увидят.
2. Ставит `m_isStopped = true` под `m_subMtx` — на случай, если
   какой-то `Publish` уже взял снимок до шага 1 и сейчас дойдёт до
   этого подписчика: он увидит флаг и не положит сообщение.
3. Дожидается `!m_isBusy` на `m_subCv` — т.е. пока пул доработает
   всё, что уже было поставлено в очередь.

**После возврата из `Unsubscribe` `handler` этого подписчика не будет
вызван ни разу.** Всё, что было вызвано до возврата, — законно
(доработка очереди, принятой до отписки).

### 8.5 Публикация в топик без подписчиков — политика

**Публикация разрешена, сообщение учитывается в статистике, но не
доставляется.**

- `Publish("nobody-here", "x")` не бросает исключение.
- `m_totalPublished` и `m_publishedPerTopic[topic]` инкрементируются.
- `m_totalDelivered` и `m_deliveredPerTopic[topic]` не меняются.
- История не хранится: подписчик, подписавшийся позже, это сообщение
  не получит.

## 9. Мониторинг состояния шины

`Monitor()` — снимок по запросу. Отдельного потока мониторинга нет.

`utils::MonitoringSnapshot` содержит:

| Поле | Что это |
|---|---|
| `m_state` | `Running` / `Stopping` / `Stopped` |
| `m_subscribersPerTopic` | число активных подписчиков по каждому топику |
| `m_publishedPerTopic` | число опубликованных сообщений по топикам |
| `m_deliveredPerTopic` | число доставленных сообщений по топикам |
| `m_totalPublished` | суммарно опубликовано |
| `m_totalDelivered` | суммарно доставлено |

Соответствие ТЗ:

- число подписчиков по каждому топику — `m_subscribersPerTopic`;
- число опубликованных и доставленных (суммарно и по топикам) —
  `m_totalPublished` / `m_totalDelivered` и
  `m_{published,delivered}PerTopic`;
- состояние шины Running / Stopping / Stopped — `m_state`.

Потокобезопасен: `m_busMtx` для подписчиков, `m_statMtx` для карт
счётчиков, атомики для тоталов. Читатель не блокирует писателей
сколько-нибудь заметно.

## 10. Демонстрационный сценарий

Реализован в
`event_bus/tests/EventBusTest.cpp`.

Шаги:
1. **Три обработчика:** `A` и `B` подписаны на `robot.state`, `C` — на
   `robot.error`.
2. **Два потока-издателя, 5 с:**
    - `P1` публикует `robot.state` каждые 50 мс;
    - `P2` публикует `robot.state` каждые 50 мс и раз в 10 итераций —
      `robot.error`.
3. **Через 3 с** вызывается `Unsubscribe(idB)`. Счётчик вызовов B
   фиксируется **сразу после возврата** из `Unsubscribe` (`hBAtUnsub`)
   вместе с временем отсечки `tUnsubReturned`.
4. **Публикация продолжается ещё 2 с** (`sleep_until(tPubStart + 5s)`).
5. **`Shutdown()`** — graceful: дожидается, пока пул доработает уже
   принятые сообщения.
6. **Подтверждение по журналу:** каждый `handler` пишет запись
   `{время, кто, payload}` в общий журнал под мьютексом. После теста
   по журналу проверяется:
    - нет ни одной записи `B` с `t > tUnsubReturned`;
    - `hB.load() == hBAtUnsub` (счётчик не вырос после отписки);
    - `A` и `C` получали сообщения (иначе сценарий не отработал);
    - `Monitor().m_state == Stopped`.

В консоль печатается сводка: число записей журнала, счётчики A/B/C,
время последнего вызова B и время отсечки, последние 5 записей B — для
визуального подтверждения.

## 11. Поведение в граничных случаях

- `Subscribe` на остановленной шине — `std::runtime_error`.
- `Publish` на остановленной шине — `std::runtime_error`.
- `Publish` с пустым топиком — `std::runtime_error`.
- `Subscribe` с пустым `handler` — `std::runtime_error`.
- `Unsubscribe` с неизвестным `id` — пишет в `stderr`.
- `Unsubscribe` повторный — пустая операция.
- `Unsubscribe` на остановленной шине — `std::runtime_error`
  (отписываться нужно до `Shutdown`).
- Исключение из `handler` перехватывается и логируется; рабочий поток
  продолжает работу.
